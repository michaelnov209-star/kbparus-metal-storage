# Безопасность проекта

## Поддерживаемая версия

Исправления безопасности вносятся в актуальную ветку разработки и после
проверок переносятся в `main`. Production должен собираться только из
зафиксированного `package-lock.json` командой `npm ci`.

## Сообщение о проблеме

Не публикуйте сведения об уязвимости в Issues. Передайте владельцу
репозитория приватно:

- затронутый URL или файл;
- условия воспроизведения;
- ожидаемое и фактическое поведение;
- возможное влияние;
- безопасный способ проверки.

Не прикладывайте токены, пароли, cookies, строки подключения и персональные
данные клиентов.

## Обязательные правила

- Секреты хранятся только в Vercel/GitHub Secrets и локальном `.env.local`.
- `PAYLOAD_SECRET` в production содержит не менее 32 случайных символов.
- Изменения схемы выполняются только контролируемыми миграциями через direct
  PostgreSQL URL; обычная сборка не должна выполнять разрушительный DDL.
- Пользовательские административные POST-запросы требуют Payload-сессию,
  проверку роли и same-origin защиту.
- Публичная форма принимает ограниченный JSON, проверяет origin, согласие,
  honeypot и durable rate limit.
- Перед релизом обязательны `npm run security:audit` и `npm run quality`.

## Реакция на инцидент

1. Отозвать затронутый токен или пароль.
2. Остановить уязвимую интеграцию без удаления данных.
3. Проверить Vercel logs, журнал заявок и административные действия.
4. Выпустить исправление через feature-ветку и preview.
5. После smoke-проверки обновить production и задокументировать причину.
